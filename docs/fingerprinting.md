# Behaviour fingerprinting

Most of the cleanup in this repo is refactoring: moving code, merging
duplicates, changing interfaces. None of that is supposed to change how the
game plays. A test suite catches broken code, but it does not catch an AI
that quietly started knocking one turn earlier. The fingerprint does.

The idea is simple. Play a fixed set of seeded games and positions, hash
what happened, and print the hashes. Before a refactor you note the hashes;
after it you run the script again. If a hash matches, every decision in
those games was identical. If it differs, something changed, and the commit
has to say what and why.

## Running it

```
uv run python scripts/fingerprint.py
```

Output as of `8bfc84d` (2026-09-29):

```
primary   basic vs context       games=150 seed=42  wins=72-78  hash=1dac7619151ab161
secondary context vs statistical  games=150 seed=42  wins=132-18  hash=e871d8e2b56ac099
scenario  quiz positions        seeds=20 seed=42  generated=20  hash=458764989f15a853
monte_carlo sequential decisions  seeds=20 seed=42 sims=40  hash=00812a7579abd075
learning  seeded training run   episodes=4 seed=42  buffer=86  hash=5727b2291609a143
learning  greedy on positions   seeds=20 seed=42  hash=9c27f019e9aee7f5
```

The whole run takes about 45 seconds. `-n` and `-s` change the game count
and seed, `--scenarios` the number of quiz positions, and `--no-learning`
skips the two torch lines.

## What each line covers

| Line | What is hashed | What it protects |
|---|---|---|
| primary | Final scores and round count of 150 BasicAI vs ContextAwareAI games | The game engine, the runner, and the two heuristic AIs. Neither AI calls `random`, so only the deck shuffle consumes the generator: a mismatch here is a real behaviour change |
| secondary | Same, ContextAwareAI vs StatisticalAI | StatisticalAI shares the global generator, so a mismatch can mean a random call moved rather than a decision changed. Read it together with primary |
| scenario | 20 positions generated by the scenario quiz: both hands, discard pile, deck order, opponent tracking, and the panel's draw advice | The quiz generator and the opponent-tracking feed |
| monte_carlo | A sequential MonteCarloAI's draw, discard and knock on the 20 scenario positions, with the expected values behind each choice | The Monte Carlo sampling, rollouts and decision logic. One worker and 40 simulations keep it deterministic and quick |
| learning, training run | Episode rewards, evaluation results and a checksum of the trained weights after 4 seeded episodes with exploration off | The trainer's round loop, experience collection and the networks |
| learning, greedy | An untrained, seeded LearningAI's draw, discard and knock on the 20 scenario positions | The learner's decision path: state encoding, context handling, network inference |

The two learning lines depend on floating point, so they only compare on the
same machine and torch build. The other four are exact everywhere.

## The workflow

1. Run the script at the commit you are about to change. Note the hashes
   (or just trust the ones in the last commit message).
2. Make the change.
3. Run the script again and compare.
4. Put the result in the commit message. Either "all six fingerprint
   lines unchanged", or the old and new hashes with an explanation of the
   behaviour change and the win rates it produced.

For an intentional change, the commit is the record. For example, commit
`2825803` rebuilt the AI's context after the draw, which moved primary from
`49ebb018605bbae6` to `1dac7619151ab161`, and its message lists every hash
that moved and a 400-game win-rate check on two seeds showing the strength
was unchanged within noise.

## What the reviewer does with it

The reviewer checks out each commit into a scratch worktree and runs the
script there:

```
git worktree add /tmp/fp/<sha> <sha>
.venv/bin/python /tmp/fp/<sha>/scripts/fingerprint.py
git worktree remove /tmp/fp/<sha>
```

The script puts its own checkout first on `sys.path`, so each run uses that
commit's code. A commit whose message says "unchanged" must reproduce the
previous hashes exactly; one that claims a behaviour change must reproduce
the new ones. The review table at the top of `AUDIT.md` records this for
every commit in a batch.

## Golden files

The fingerprint hashes outcomes. For things where the exact stored data
matters, `tests/golden/` holds the data itself:

- `turn_rows_cli_seed7.json` and `turn_rows_web_seed7.json`: the database
  rows a seeded round writes through the CLI and the web session.
- `scenarios_seed7.json`: five generated quiz positions in full.

These run as ordinary tests, so CI catches a change. When a change is
intentional, rerun the owning test with `UPDATE_GOLDEN=1` set, for example
`UPDATE_GOLDEN=1 uv run pytest tests/test_scenario_quiz.py`, and commit the
new file with the reason.

## What it does not catch

- Any code path the seeded runs never reach. The Monte Carlo line runs
  with one worker because worker processes reseed from the pid and clock,
  so the process-pool path itself is only covered by tests.
- Changes under non-default configuration. The primary line plays with the
  default config; ContextAwareAI's live-outs discard logic, for example, is
  off by default and therefore untested here.
- Non-determinism from hash ordering. `Card.__hash__` is stable, and the
  script re-executes itself with `PYTHONHASHSEED=0` anyway, so set iteration
  order cannot move a result.

A matching hash means "nothing in these runs changed", not "nothing
changed". When a refactor touches code the lines do not reach, add a line
first, then refactor.
